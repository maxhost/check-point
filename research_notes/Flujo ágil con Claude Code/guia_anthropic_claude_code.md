## 1. CLAUDE.md: tamano, contenido, imports, anidados

### Takeaway
Anthropic fija un numero concreto: **menos de 200 lineas por archivo CLAUDE.md**, solo lo que aplica a *toda* sesion y que Claude no puede inferir del codigo. Procedimientos y conocimiento de un dominio van a skills o a reglas con `paths:`; los imports `@` **no** ahorran contexto (cargan al inicio igual). Lo que debe cumplirse siempre va en hooks, no en CLAUDE.md.

### Cited Findings
- **Limite numerico:** "Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." — [Memory docs](https://code.claude.com/docs/en/memory) (vigente 2026-10). Repetido como "Rule of thumb: Keep CLAUDE.md under 200 lines. If it's growing, move reference content to skills or split into `.claude/rules/` files." — [Extend Claude Code](https://code.claude.com/docs/en/features-overview); y "Aim to keep CLAUDE.md under 200 lines by including only essentials." — [Costs](https://code.claude.com/docs/en/costs).
- Claude Code **avisa al arrancar** si un archivo pasa el largo recomendado, y tambien si varios archivos dentro del limite "add up past a combined limit at session start. Each CLAUDE.md, rules file, and `@path` import counts as a separate file." Ignora archivos de mas de 4 MiB. — [Memory docs](https://code.claude.com/docs/en/memory)
- **Criterio de poda:** "Keep it concise. For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Sintoma de archivo demasiado largo:** "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Anti-patron explicito "The over-specified CLAUDE.md": "If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise. Fix: Ruthlessly prune. If Claude already does something correctly without the instruction, delete it or convert it to a hook." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Tabla incluir / excluir** (cita textual): Incluir — "Bash commands Claude can't guess", "Code style rules that differ from defaults", "Testing instructions and preferred test runners", "Repository etiquette (branch naming, PR conventions)", "Architectural decisions specific to your project", "Developer environment quirks (required env vars)", "Common gotchas or non-obvious behaviors". Excluir — "Anything Claude can figure out by reading code", "Standard language conventions Claude already knows", "Detailed API documentation (link to docs instead)", "Information that changes frequently", "Long explanations or tutorials", "File-by-file descriptions of the codebase", "Self-evident practices like 'write clean code'". — [Best practices](https://code.claude.com/docs/en/best-practices)
- "CLAUDE.md is loaded every session, so only include things that apply broadly. For domain knowledge or workflows that are only relevant sometimes, use skills instead." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "Keep it to facts Claude should hold in every session: build commands, conventions, project layout, 'always do X' rules. If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead." — [Memory docs](https://code.claude.com/docs/en/memory)
- **Enfasis:** "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Especificidad y estructura:** "Make instructions more specific. 'Use 2-space indentation' works better than 'format code nicely.'"; "group related instructions under markdown headers and bullets. Organized sections are easier for Claude to follow than dense paragraphs." — [Memory docs](https://code.claude.com/docs/en/memory)
- **Contradicciones:** "if two instructions contradict each other, Claude may pick one arbitrarily." Se recomienda `/doctor prompt-audit` (v2.1.283+) que busca "instructions written for older models, references to files or commands that don't exist, and files that contradict each other". Y para un CLAUDE.md commiteado, "run `/doctor` and Claude proposes cuts for content it can derive from the codebase." — [Memory docs](https://code.claude.com/docs/en/memory); [Best practices](https://code.claude.com/docs/en/best-practices)
- **No es enforcement:** "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but there's no guarantee of strict compliance". "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." — [Memory docs](https://code.claude.com/docs/en/memory)
- **Imports `@`:** "Imported files are expanded and loaded into context at launch alongside the CLAUDE.md that references them." Profundidad maxima 4 saltos. "Imports help you organize a long file but don't reduce its context cost, because imported files also load at launch." Un path entre backticks no se importa. — [Memory docs](https://code.claude.com/docs/en/memory)
- **CLAUDE.md anidados:** los de directorios superiores cargan al inicio; "Files in subdirectories load on demand when Claude reads files in those directories." — [Memory docs](https://code.claude.com/docs/en/memory)
- **Reglas con `paths:`** (`.claude/rules/*.md`): "only load into context when Claude works with matching files, reducing noise and saving context space". Sin `paths`, cargan al inicio como CLAUDE.md. — [Memory docs](https://code.claude.com/docs/en/memory)
- **Comentarios HTML gratis:** "Block-level HTML comments (`<!-- maintainer notes -->`) in CLAUDE.md files are stripped before the content is injected into Claude's context. Use them to leave notes for human maintainers without spending context tokens on them." — [Memory docs](https://code.claude.com/docs/en/memory)
- **Construir el setup por disparadores, no de antemano:** "You don't need to configure everything up front." Tabla: "Claude gets a convention or command wrong twice → Add it to CLAUDE.md"; "You paste the same playbook or multi-step procedure into chat for the third time → Capture it as a skill"; "You want something to happen every time without asking → Write a hook". — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- **Blog oficial (18-jun-2026, Michael Segner, Anthropic):** "Keep CLAUDE.md under 200 lines, give it an owner, and review changes to it like code." "Instructions that are procedural, like deploy workflows, release checklists, or review processes, belong in a skill rather than in CLAUDE.md." Anti-patron: procedimientos de ~30 lineas dentro de CLAUDE.md. — [Steering Claude Code (claude.com/blog)](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- **Auto memory (MEMORY.md):** se cargan "the first 200 lines of MEMORY.md, or the first 25KB, whichever comes first"; el resto no. Los topic files no se cargan al inicio: "Claude reads them on demand". — [Memory docs](https://code.claude.com/docs/en/memory)
- **Costo representativo** en la simulacion oficial: system prompt ~4.200 tokens, CLAUDE.md de proyecto ~1.800, descripciones de skills ~450, MEMORY.md ~680, MCP diferido ~120 (numeros "representativos", no medidos del usuario). — [Context window](https://code.claude.com/docs/en/context-window)

### Inferences
- El limite es de **lineas**, pero el costo real es de tokens: un archivo de 199 lineas con parrafos largos (el CLAUDE.md de este repo mide 199 lineas y ~14,3 KB) cumple la letra del limite y no su espiritu. El objetivo de Anthropic es "solo lo que cambia una decision en toda sesion", y la tabla "excluir" incluye "long explanations" y casos historicos.
- Las secciones de "Verificacion" del repo que narran casos ("en la 0080…", "en la 0068…") son el tipo de contenido que la guia manda a otro lado (explicaciones largas / informacion que cambia). Anthropic sugiere: regla corta en CLAUDE.md, procedimiento en skill, enforcement en hook.
- La sugerencia de enfasis ("IMPORTANT en una sola linea") choca con un archivo donde muchas lineas van en negrita/mayusculas: segun la guia, eso diluye todas.

### Gaps
- Anthropic no da un limite en **tokens** para CLAUDE.md ni publica el valor exacto del "combined limit" que dispara el aviso de inicio.
- No hay una fecha de "ultima actualizacion" visible en las paginas de docs.

## 2. Gestion de contexto: /clear vs compactacion, ventana chica, skills, memoria

### Takeaway
Para Anthropic el contexto es "el recurso mas importante a gestionar". Recomienda **`/clear` entre tareas no relacionadas** (cuesta cero) y tras dos correcciones fallidas; la compactacion existe y es legitima (automatica, `/compact <foco>`, resumir parcial con `/rewind`), pero compactar un contexto grande es una request cara. El estado que debe sobrevivir va a disco (CLAUDE.md, archivos de progreso, git).

### Cited Findings
- "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." "The context window is the most important resource to manage." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "Use `/clear` frequently between tasks to reset the context window entirely". "/clear: reset context between unrelated tasks. Long sessions with irrelevant context can reduce performance." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Regla de las dos correcciones:** "If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run `/clear` and start fresh with a more specific prompt that incorporates what you learned. A clean session with a better prompt almost always outperforms a long session with accumulated corrections." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Compactacion no esta desaconsejada: "When auto compaction triggers, Claude summarizes what matters most, including code patterns, file states, and key decisions"; "For more control, run `/compact <instructions>`"; se puede instruir en CLAUDE.md "When compacting, always preserve the full list of modified files and any test commands". — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Costo:** "`/compact` reads the conversation it summarizes, so compacting a large context is itself a large request. When you want a fresh start instead of continuity, `/clear` costs nothing". — [Costs](https://code.claude.com/docs/en/costs)
- "Use `/rename` before clearing so you can easily find the session later, then `/resume` to return to it." — [Costs](https://code.claude.com/docs/en/costs)
- **Que sobrevive a la compactacion** (tabla oficial): CLAUDE.md raiz y reglas sin `paths` → "Re-injected from disk"; auto memory → re-inyectada; el plan de plan mode → re-inyectado; hasta 5 archivos leidos/editados se releen; cuerpos de skills invocadas re-inyectados "capped at 5,000 tokens per skill and 25,000 tokens total"; CLAUDE.md anidados y reglas con `paths:` solo se recargan cuando se vuelve a leer un archivo que matchea. "If an instruction disappeared after compaction, it was given only in conversation". — [Context window](https://code.claude.com/docs/en/context-window); [Memory docs](https://code.claude.com/docs/en/memory)
- Truncado de skills al compactar: "Truncation keeps the start of the file, so put the most important instructions near the top of `SKILL.md`." — [Context window](https://code.claude.com/docs/en/context-window)
- Hook `SessionStart` con matcher `compact` para re-inyectar contexto critico tras cada compactacion. — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `/btw` para preguntas laterales: "The answer never enters conversation history". — [Best practices](https://code.claude.com/docs/en/best-practices)
- Subagentes como herramienta de contexto: "Since context is your fundamental constraint, use subagents to keep research out of it." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Ventana de 1M en Sonnet 5/5.5, Opus 4.6+ y Fable; auto-compact por defecto en ~967K para modelos de 1M nativo; configurable con `/autocompact 500k`. — [Context window](https://code.claude.com/docs/en/context-window); [Model config](https://code.claude.com/docs/en/model-config)
- Sesiones largas suben el consumo: cada request reenvia toda la conversacion; el primer mensaje tras una pausa mayor al TTL del cache (1 h en suscripcion; 5 min por defecto con API key o usage credits) reprocesa todo. — [Costs](https://code.claude.com/docs/en/costs)
- **Engineering blog (29-sep-2025)** "Effective context engineering for AI agents": "context rot: as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"; objetivo: "find the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"; Claude Code es hibrido: "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time"; subagentes devuelven "a condensed, distilled summary of its work (often 1,000-2,000 tokens)"; recomienda notas estructuradas en archivos (p.ej. NOTES.md). — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Engineering blog (26-nov-2025)** "Effective harnesses for long-running agents": usar `claude-progress.txt`, lista de features en JSON, "work on only one feature at a time. This incremental approach turned out to be critical"; "commit its progress to git with descriptive commit messages and to write summaries of its progress in a progress file"; al inicio "Read the git logs and progress files to get up to speed". — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

### Inferences
- La practica del repo "handoff a disco y despues /clear" esta alineada con Anthropic. La regla absoluta "nunca compact" es **mas estricta** que la guia: Anthropic presenta `/compact <foco>` y "Summarize from here" como herramientas validas, y documenta que CLAUDE.md raiz, auto memory y el plan se re-inyectan desde disco. La diferencia real es de costo (compactar un contexto grande es caro; `/clear` es gratis), no de prohibicion.
- El patron "archivo de estado + git log al arrancar" del repo coincide con el del post de harnesses; la diferencia es de volumen: Anthropic lo plantea como un archivo de progreso corto + git, no como multiples docs obligatorios por tarea.

### Gaps
- Anthropic no da un umbral recomendado de "% de contexto" para hacer `/clear` manual; solo criterios cualitativos (tarea no relacionada, dos correcciones fallidas).

## 3. Skills y hooks: para que son, como cargan, que se hace deterministico

### Takeaway
Skills = conocimiento/procedimientos **bajo demanda**: solo la descripcion vive en cada request (truncada a 1.536 caracteres), el cuerpo carga al invocarse; con `disable-model-invocation: true` cuestan cero hasta usarse. Hooks = lo que **debe** pasar siempre; costo de contexto cero salvo que devuelvan salida. "Put guardrails in hooks."

### Cited Findings
- "Unlike CLAUDE.md content, a skill's body loads only when it's used, so long reference material costs almost nothing until you need it." — [Skills docs](https://code.claude.com/docs/en/skills)
- Pero no es gratis del todo: "Every skill in the skill listing adds to your context on every turn, whether or not Claude ever uses it. Run `/skill-doctor` to see what each of your skills costs and how often it gets used." La descripcion + `when_to_use` "is truncated at 1,536 characters in the skill listing". — [Skills docs](https://code.claude.com/docs/en/skills)
- "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files." — [Skills docs](https://code.claude.com/docs/en/skills)
- Una vez invocada, "the rendered SKILL.md content enters the conversation as a single message and stays there across later turns." — [Skills docs](https://code.claude.com/docs/en/skills)
- Cuando crear una skill: "You keep pasting the same instructions, checklist, or multi-step procedure into chat"; "A section of CLAUDE.md has grown into a procedure rather than a fact". — [Skills docs](https://code.claude.com/docs/en/skills)
- `disable-model-invocation: true`: Claude no la invoca solo y "Description does NOT load into context"; "User-only skills have zero cost until invoked." Recomendado "for skills with side effects. This saves context and ensures they run only when you name them." — [Skills docs](https://code.claude.com/docs/en/skills); [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- `context: fork` corre la skill en un subagente aislado. — [Skills docs](https://code.claude.com/docs/en/skills)
- Si las descripciones son vagas o se solapan, "Claude may load the wrong skill or miss one that would help". — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- **Engineering blog (16-oct-2025, actualizado 18-dic-2025 como estandar abierto)** "Equipping agents for the real world with Agent Skills": tres niveles de divulgacion progresiva (metadata → SKILL.md → archivos adicionales); "the amount of context that can be bundled into a skill is effectively unbounded"; empezar por evaluacion ("running them on representative tasks and observing where they struggle"). — [Anthropic Engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- **Hooks:** "Use hooks for actions that must happen every time with zero exceptions." "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "Put guardrails in hooks. An instruction like 'never edit .env' in CLAUDE.md or a skill is a request, not a guarantee. A PreToolUse hook that blocks the edit is enforcement." "Use a hook when the action must happen the same way every time and doesn't need Claude to think." Costo: "Zero unless the hook returns output". — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- "If the instruction is something that must run at a specific point, such as before every commit or after each file edit, write it as a hook instead." — [Memory docs](https://code.claude.com/docs/en/memory)
- Hooks para recortar contexto: un hook puede filtrar salida (p.ej. tests → solo fallos), "reducing context from tens of thousands of tokens to hundreds". — [Costs](https://code.claude.com/docs/en/costs)
- Hooks de juicio: `type: "prompt"` (timeout 30 s) y `type: "agent"` (60 s, hasta 50 turnos) "for decisions that require judgment rather than deterministic rules". Timeouts por defecto de hooks command: 10 min. — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **Stop hooks:** "Stop hooks fire whenever Claude finishes responding, not only at task completion." Claude Code anula un Stop hook "after it blocks eight times in a row without progress"; el script debe chequear `stop_hook_active`. — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Stop hook como gate deterministico de verificacion: "a Stop hook runs your check as a script and blocks the turn from ending until it passes." — [Best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- Un Stop hook que corre typecheck+lint+test **en cada fin de respuesta** (no solo al terminar la tarea) agrega esa latencia a cada turno, incluidos los conversacionales; la guia aclara que Stop dispara en cada respuesta. Es un candidato directo a "turnos lentos".
- Cada skill con descripcion larga suma tokens en **cada** request; `/skill-doctor` mide cuanto. Skills de uso manual (handoff, QA temporal) pueden pasar a `disable-model-invocation: true` para costar cero.

### Gaps
- No encontre una cifra oficial de cuantos hooks/skills es "demasiado"; solo la herramienta `/skill-doctor` y el aviso de que cada una cuesta por turno.

## 4. Flujos recomendados para velocidad

### Takeaway
Explorar → planificar → codear → commitear para cambios inciertos o multi-archivo; **darle a Claude un check que pueda correr** (lo mas enfatizado); sesiones paralelas en worktrees; revisor en contexto fresco al final; modelo/esfuerzo/fast mode segun la tarea.

### Cited Findings
- **Verificacion (tip principal):** "Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from." "Have Claude show evidence rather than asserting success". Niveles: en el prompt, `/goal`, Stop hook, o subagente verificador; "Each step trades setup for attention." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Explore → Plan → Implement → Commit** con plan mode (`Shift+Tab`, `Ctrl+G` para editar el plan). — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Spec para features grandes:** "For larger features, have Claude interview you first"; luego "start a fresh session to execute it"; "The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step". — [Best practices](https://code.claude.com/docs/en/best-practices)
- **TDD / tests primero:** "write a failing test that reproduces the issue, then fix it"; patron "have one Claude write tests, then another write code to pass them." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Revisor adversarial, con limite:** "Before treating a task as done, have a subagent review the diff in a fresh context and report gaps." Advertencia: "A reviewer prompted to find gaps will usually report some, even when the work is sound… Chasing every finding leads to over-engineering… Tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional." Hay skill integrada `/code-review`. — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Paralelismo:** worktrees, mensajeria entre sesiones, agent view (research preview), agent teams (experimental, apagado por defecto); patron Writer/Reviewer. `/batch` reparte un cambio en 5 a 30 subagentes, cada uno en su worktree. — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Worktrees:** `claude --worktree <nombre>` crea `.claude/worktrees/<nombre>/` en rama `worktree-<nombre>`; "A worktree is a fresh checkout, so initialize your development environment there"; `.worktreeinclude` copia gitignored como `.env`; subagentes con `isolation: worktree`. — [Worktrees](https://code.claude.com/docs/en/worktrees)
- **Headless:** `claude -p`, `--output-format json|stream-json`, `--allowedTools`, `--permission-mode dontAsk` para lotes. — [Best practices](https://code.claude.com/docs/en/best-practices)
- **Modelos:** "Sonnet handles most coding tasks well and costs less than Opus. Reserve Opus for complex architectural decisions or multi-step reasoning." "For simple subagent tasks, specify `model: haiku`." — [Costs](https://code.claude.com/docs/en/costs). Alias `opusplan`: "In plan mode: uses opus… In execution mode: automatically switches to sonnet". Default actual en Pro/Max/Team/Enterprise/API: Opus 5.5. — [Model config](https://code.claude.com/docs/en/model-config)
- **Esfuerzo:** `low` = "Quick exchanges where you review each result, such as brainstorming, a first sketch, or a small change like a rename"; `medium` = default en Opus 5.5 y Sonnet 5.5, "day-to-day engineering work with a clear scope". — [Model config](https://code.claude.com/docs/en/model-config)
- **Fable 5.1 / 5:** "Skip the verification reminders: it verifies its own work with less prompting, so reminders to test or check are usually unnecessary." "Describe the outcome, not the steps". No es default en ningun plan. — [Model config](https://code.claude.com/docs/en/model-config)
- **Fast mode (research preview):** "making the model up to 2.5x faster at a higher cost per token"; mismo modelo y calidad; solo Opus 5.5/5/4.8; $8/$40 por MTok en Opus 5.5; en suscripcion se paga solo con usage credits. Usar para "Rapid iteration… Live debugging"; no para tareas autonomas largas, CI o costo-sensibles. Activarlo al inicio de la sesion es mas barato. Combinable con esfuerzo bajo "for maximum speed on straightforward tasks". — [Fast mode](https://code.claude.com/docs/en/fast-mode)
- **Permisos / auto mode:** desde v2.1.283 auto mode es el modo inicial por defecto en terminal y VS Code: "a separate classifier model reviews most actions instead of you and blocks only what looks risky". Bloquea por defecto: `curl | bash`, deploys/migraciones a produccion, force push, `git reset --hard`, etc. Respeta limites dichos en la conversacion ("don't push"). Se pausa tras 3 bloqueos seguidos o 20 totales. Lecturas y ediciones en el working dir se saltean el clasificador (la latencia extra viene de shell/red). `bypassPermissions`: "Isolated containers and VMs only". — [Permission modes](https://code.claude.com/docs/en/permission-modes); [Best practices](https://code.claude.com/docs/en/best-practices)
- "After the tenth approval you're clicking through rather than reviewing." Recomienda allowlists (`/permissions`) y sandbox (`/sandbox`). — [Best practices](https://code.claude.com/docs/en/best-practices)
- **CLI sobre MCP:** "CLI tools are the most context-efficient way to interact with external services." — [Best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- Con Opus 5.5 en esfuerzo `medium` por defecto, el trabajo chico ya puede ir en `low`; las tareas grandes y autonomas, en `high` o en Fable. Fast mode ataca la latencia sin perder calidad, a costa de plata.
- La advertencia de Anthropic sobre revisores que "siempre encuentran algo" sugiere acotar el encargo del revisor a correccion y requisitos, no a exhaustividad.

### Gaps
- No hay benchmarks oficiales de cuanto tiempo ahorra cada practica (salvo el "up to 2.5x" de fast mode).

## 5. Escalar el proceso al tamano de la tarea

### Takeaway
Anthropic lo dice explicitamente: **si podes describir el diff en una oracion, salteate el plan**; plan mode "agrega overhead" y es para enfoques inciertos, cambios multi-archivo o codigo desconocido. Las specs con entrevista son para features grandes.

### Cited Findings
- "Plan mode is useful, but also adds overhead. For tasks where the scope is clear and the fix is small (like fixing a typo, adding a log line, or renaming a variable) ask Claude to do it directly. Planning is most useful when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code being modified. If you could describe the diff in one sentence, skip the plan." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "For larger features, have Claude interview you first" (no para todo cambio). — [Best practices](https://code.claude.com/docs/en/best-practices)
- "Each step trades setup for attention. The prompt version works on any task today. The /goal and Stop hook versions are what let an unattended run finish correctly without you." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "The longer Claude works unattended, the more an independent check matters before you count the work as done." (la revision independiente escala con la autonomia, no es fija). — [Best practices](https://code.claude.com/docs/en/best-practices)
- "Develop your intuition: … Sometimes you should skip planning and let Claude figure it out because the task is exploratory." "They're starting points that work well in general, but might not be optimal for every situation." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Esfuerzo `low` para "a small change like a rename". — [Model config](https://code.claude.com/docs/en/model-config)
- "Vague prompts can be useful when you're exploring and can afford to course-correct." — [Best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- Un flujo que exige spec cerrada + ADR + fila en INDEX + implementador + revisor para **todo** cambio que toque codigo va en contra de la guia para cambios de una oracion. La guia es compatible con mantener spec + revisor para features grandes o trabajo autonomo largo, y con un carril rapido (pedido directo + check ejecutable) para fixes chicos.
- La propia evidencia que cita el repo (reward hacking alto en tareas vagas) se puede leer a favor de un carril rapido: un fix de una oracion ya es una tarea "bien definida"; lo que la protege es el check ejecutable, no el documento.

### Gaps
- Anthropic no define umbrales cuantitativos (lineas, archivos) para pasar de "pedido directo" a "plan" o "spec"; el criterio es cualitativo ("describir el diff en una oracion").
- No encontre guia oficial sobre ADRs ni sobre docs de decision en el repo; es practica propia del equipo, ni recomendada ni desaconsejada.
